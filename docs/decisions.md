# Project Albedo: Architectural Decisions Log

This document serves as the historical record for the major engineering trade-offs made during the development of **Project Albedo**. It documents and justifies the architectural choices across the **mathematics**, **graphics**, and **systems architecture** domains.

---

## Mathematical Framework: Rectified Flow vs. Standard Diffusion (DDPM)

### Decision

We use **Rectified Flow** (Continuous Normalizing Flows via ODEs) instead of standard **Diffusion Models** (SDEs) as the neural rendering backbone.

### Alternative Considered

- Denoising Diffusion Probabilistic Models (DDPM)
- Latent Diffusion Models (e.g., Stable Diffusion)

### Rationale

Standard diffusion models rely on **Stochastic Differential Equations (SDEs)**, which iteratively inject and remove Gaussian noise along curved probability trajectories. Recovering a clean image therefore requires dozens—or even hundreds—of numerical solver steps, making real-time rendering impractical.

Rectified Flow instead learns a **deterministic vector field** that transports samples along nearly straight trajectories between the prior distribution (our **1-SPP noisy render**) and the target distribution (the clean image). Since these trajectories are approximately linear, the corresponding **Ordinary Differential Equation (ODE)** can be solved using a single Euler discretization step:

\[
X_{$\text{clean}$} = X_0 + v_$\theta$(X_0)
\]

This reduces inference latency from **seconds to milliseconds**, making interactive frame rates feasible while maintaining high reconstruction quality.

## Rendering Engine: Taichi vs. C++/OptiX

### Decision

The ray tracer and BVH traversal are implemented in **Python using Taichi (`@ti.kernel`)**.

### Alternative Considered

- Standalone C++ rendering engine
- NVIDIA OptiX utilizing hardware RT Cores
- Python bindings through `pybind11`

### Rationale

A C++/OptiX implementation offers the highest possible raw ray-tracing performance through dedicated RT Cores. However, during active AI research and rapid experimentation, maintaining a mixed C++/Python codebase introduces significant development overhead and slows iteration.

Taichi provides an excellent compromise by compiling Python kernels directly into optimized CUDA code while integrating seamlessly with PyTorch.

This enables one of the project's most important optimizations:

> **Zero-Copy VRAM Sharing**

Instead of copying rendered G-buffer data through the expensive path

```bash
GPU → CPU → GPU
```

Taichi writes directly into **pre-allocated PyTorch tensors** residing in GPU memory.

This completely removes PCIe transfer overhead and significantly reduces rendering latency.

Although Taichi executes on standard CUDA cores rather than dedicated RT Cores, its performance is sufficient to render the **1-SPP G-buffer in approximately 2–3 ms**, leaving the remainder of the **16 ms frame budget** available for neural inference.

A future production version could replace Taichi with an optimized OptiX backend if additional rendering performance becomes necessary.

## Distributed Workload: Java Microservice vs. Python Monolith

### Decision

Procedural terrain generation (Marching Cubes) is implemented as an independent **Java microservice**.

### Alternative Considered

Implementing procedural generation directly inside the Python rendering process.

### Rationale

Python's **Global Interpreter Lock (GIL)** limits the scalability of CPU-bound multithreaded workloads.

Procedural terrain generation—including:

- 3D Perlin noise evaluation
- Density field computation
- Marching Cubes mesh extraction

requires processing millions of voxels and is heavily CPU-intensive.

By isolating this workload inside a dedicated Java service, we leverage:

- JVM-optimized multithreading
- Efficient garbage collection
- Mature concurrency primitives

This architecture enables simultaneous hardware utilization:

- **CPU:** Fully utilized by Java
- **GPU:** Fully utilized by Python/CUDA

Mesh data generated by Java is serialized and streamed to the Python renderer via **gRPC**, ensuring that procedural generation never blocks the neural rendering pipeline.

## Network Transport: Node.js/WebSockets vs. FastAPI Native

### Decision

A lightweight **Node.js proxy server** manages WebSocket communication instead of exposing WebSockets directly through the FastAPI AI server.

### Alternative Considered

Connecting the React frontend directly to the FastAPI backend via WebSockets.

### Rationale

Python ASGI servers such as **Uvicorn** excel at orchestrating asynchronous machine learning workloads but are not optimized for managing large numbers of persistent, high-frequency WebSocket connections.

Node.js, powered by the **V8 JavaScript engine**, provides highly efficient event-driven socket management.

Introducing a Node.js proxy creates a dedicated networking layer responsible for:

- Client session management
- Connection lifecycle handling
- Automatic reconnection support
- Frame buffering
- Request queueing
- Connection multiplexing

This separation allows the FastAPI backend to focus exclusively on GPU inference.

When multiple clients connect simultaneously, the Node.js layer can queue rendering requests, preventing the single **RTX 5070 Ti** from becoming overwhelmed by concurrent tensor initialization or GPU scheduling conflicts.

The result is a more resilient and scalable architecture with clear separation of concerns between networking and AI inference.

## Frontend Rendering: 2D HTML Canvas vs. Three.js

### **Decision** 

- The frontend is a simple React application using a standard 2D HTML `<canvas>` to paint incoming image bytes, completely omitting 3D libraries like Three.js

### **Alternative Considered**

- Using Three.js or React Three Fiber to handle the 3D environment.

### **Rationale**

Three.js is a client-side WebGL/WebGPU library. It requires sending the actual 3D geometry (millions of vertices generated by our Java engine) over the network to the user's browser, where their local GPU rasterizes it.
Project Albedo is a server-side Neural Renderer. The entire point of our AI pipeline is that the Taichi engine and PyTorch model must process the geometry locally on the server's RTX 5070 Ti to perform the Rectified Flow denoising. The frontend does not render 3D at all; it acts as a "dumb terminal" that simply captures mouse/keyboard input and displays a rapid stream of 2D WebP images (the final output of the AI). Using Three.js would bypass our neural engine entirely and fry the user's laptop.
